# Онбординг — API

Платформа интерактивного онбординга: админка создаёт туры, SDK получает опубликованную
версию и показывает подсказки поверх чужого DOM, бэк принимает события и считает воронку.

Базовый URL: `http://localhost:8080/v1`

Это справочник по ручкам. Как система живёт во времени — в каком порядке всё вызывается,
что происходит при смене версии посреди прохождения, чем «выключить» отличается
от «удалить» — в [onboarding-flows.md](onboarding-flows.md).

Машиночитаемая схема — `docs/swagger.json`, генерируется `swag init`. Этот файл писан
руками и лежит в корне намеренно: `docs/` принадлежит генератору и вычищается им при каждом
запуске.

## Модель за пять строк

- **Тур** — стабильная сущность. Живёт вечно, у него нет собственного статуса.
- **Версия тура** — конкретная редакция. Иммутабельна. Ровно одна может быть `published`
  и ровно одна `draft` (гарантия — частичные уникальные индексы).
- **Подсказка** — принадлежит **версии**, а не туру. Поэтому «опубликованное не меняется»
  распространяется и на подсказки: править можно только черновик.
- **Прогресс** — единственная мутабельная таблица: где остановился конкретный пользователь.
- **Событие** — сырой лог аналитики. Каждое несёт `tour_version_id`, иначе воронка
  смешала бы показы до и после правки текстов.

Правка опубликованного тура = `POST /draft` (форк) → правки → `POST /publish`.

## Аутентификация

> **Авторизации пользователя сейчас нет.** Она отложена: все админские ручки открыты,
> и любой вызывающий считается одним и тем же замоканным администратором. Сервис пишет
> об этом `WARN` при старте, чтобы открытое развёртывание было видно в логах, а не
> обнаруживалось.
>
> Это нормально для локальной разработки и не нормально нигде больше: под `/v1/tours`
> лежат публикация, откат и архивация.

| Группа | Заголовок | Статус |
|---|---|---|
| Рантайм (SDK) | `X-App-Key: <public_key>` | Обязателен |
| Админка | — | Открыта |

`X-App-Key` остаётся и к отложенной авторизации отношения не имеет: это идентификация
**приложения**, без которой `/resolve` не знает, чьи туры искать.

`public_key` не секрет — он виден в исходниках страницы. Поэтому он не даёт ничего писать,
а `allowed_origins` приложения работает белым списком для CORS: чужой сайт с вашим ключом
не сможет набить вам аналитику мусором. Origin, которого нет в списке, получает `403`.

## Формат ошибок

Единый для всех эндпоинтов.

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Tour cannot be published",
    "details": [
      { "path": "hints[0].selector", "message": "required unless placement is center" }
    ]
  }
}
```

`details` заполняется там, где ошибка привязана к полю — в первую очередь при публикации.
Без него `422` на туре из двадцати подсказок сообщает админу только то, что где-то что-то не так.

Коды: `BAD_REQUEST` (400), `UNAUTHORIZED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404),
`CONFLICT` (409), `VALIDATION_FAILED` (422), `INTERNAL` (500).

## Туры

### `POST /v1/tours` — создать тур

Создаёт тур **вместе с пустым черновиком v1** в одной транзакции: тур без версии — состояние,
которое редактору нечем отрисовать.

Request:

`appId` - uuid - приложение, которому принадлежит тур (query)

```json
{
  "title": "Публикация объявления",
  "description": "Проводим нового пользователя до публикации",
  "trigger_type": "on_load",
  "target_path": "/additem*",
  "priority": 10,
  "audience": { "show_once": true, "max_shows": 0, "only_new": false }
}
```

- `trigger_type` — `on_load` | `delay` | `exit_intent` | `manual`
- `target_path` — glob-паттерн (`*` = любые символы), не regex: админ пишет его руками
- `priority` — больше = важнее при конкуренции нескольких туров
- `audience.max_shows` — `0` означает без ограничения

Response `201`:

```json
{
  "id": "08c786e1-19f8-4ffb-b850-c353c62185cc",
  "app_id": "73d31e53-3a7b-48c0-93a9-36ec63ffbecd",
  "title": "Публикация объявления",
  "description": "Проводим нового пользователя до публикации",
  "enabled": false,
  "priority": 10,
  "created_at": "2026-08-07T14:55:39.85Z",
  "updated_at": "2026-08-07T14:55:39.85Z",
  "version_id": "c82c240c-2195-4647-86ac-415caf2788e0",
  "version": 1,
  "status": "draft",
  "trigger_type": "on_load",
  "target_path": "/additem*",
  "audience": { "show_once": true, "max_shows": 0, "only_new": false },
  "hints": []
}
```

### `GET /v1/tours` — список туров

Каждый тур отдаётся вместе с той версией, которая интересна админу: опубликованной,
а если её нет — самой свежей.

Request:

`appId` - uuid - приложение

Response `200`: массив туров в форме из ответа выше.

### `GET /v1/tours/{tourId}` — карточка тура

Тур и **обе** версии, которые могут существовать одновременно. Отдаются вместе, чтобы
редактор рисовал две колонки за один запрос, а не за три.

Request: `none`

Response `200`:

```json
{
  "tour": {
    "id": "08c786e1-19f8-4ffb-b850-c353c62185cc",
    "app_id": "73d31e53-3a7b-48c0-93a9-36ec63ffbecd",
    "title": "Публикация объявления",
    "description": "Проводим нового пользователя до публикации",
    "enabled": true,
    "priority": 10,
    "created_at": "2026-08-07T14:55:39.85Z",
    "updated_at": "2026-08-07T14:55:39.93Z"
  },
  "published": {
    "id": "8176e13d-d474-447f-abf0-f5b82a0cdbf6",
    "tour_id": "08c786e1-19f8-4ffb-b850-c353c62185cc",
    "version": 3,
    "status": "published",
    "trigger_type": "on_load",
    "target_path": "/additem*",
    "audience": { "show_once": true, "max_shows": 0, "only_new": false },
    "created_at": "2026-08-07T14:55:40.15Z",
    "published_at": "2026-08-07T14:55:40.15Z",
    "hints": [ "...см. раздел Подсказки..." ]
  },
  "draft": null
}
```

Поля версии на объекте `tour` отсутствуют намеренно: они лежат в `published` и `draft`,
а пустые строки читались бы как «у тура нет target_path».

### `PATCH /v1/tours/{tourId}` — изменить метаданные

Меняет то, что **не является содержанием версии**, и потому новую версию не создаёт.
Выключение тура — это рубильник, а не редакция: плодить из-за него версию значит рвать
статистику на ровном месте.

Request:

```json
{ "title": "Новое название", "description": "...", "enabled": true, "priority": 20 }
```

Все поля опциональны, передавать можно любое подмножество.

Response `200`:

```json
{
  "id": "08c786e1-19f8-4ffb-b850-c353c62185cc",
  "app_id": "73d31e53-3a7b-48c0-93a9-36ec63ffbecd",
  "title": "Публикация объявления",
  "description": "Проводим нового пользователя до публикации",
  "enabled": true,
  "priority": 10,
  "created_at": "2026-08-07T14:55:39.85Z",
  "updated_at": "2026-08-07T14:55:39.93Z"
}
```

### `DELETE /v1/tours/{tourId}` — заархивировать тур

Мягкое удаление. Жёсткое унесло бы с собой историю аналитики, и схема его всё равно
не пропустит через `ON DELETE RESTRICT`.

Request: `none`

Response `204`, без тела.

### `GET /v1/tours/published` — опубликованные туры по пути

Для админки и предпросмотра: «что сейчас живёт на этой странице». SDK ходит в `/resolve`,
который дополнительно знает про пользователя.

Request:

`appId` - uuid - приложение
`path` - string - путь страницы, например `/additem`

Response `200`: массив туров с подсказками.

### `GET /v1/versions/{versionId}` — одна версия

С подсказками — для диффа и предпросмотра старой редакции. Подсказки здесь и есть смысл
ручки: версия без них не показывает, что изменилось.

Request: `none`

Response `200`: объект версии из ответа выше плюс поле `hints` с полным списком подсказок
(структура — см. раздел «Подсказки»).

### `POST /v1/tours/{tourId}/draft` — форкнуть черновик

Точка входа в редактирование. Копирует опубликованную версию и **её строки подсказок**
в новую версию со статусом `draft`. Сама опубликованная версия не трогается никогда.

Request: `none`

Response `201`:

```json
{
  "id": "480026e1-3079-4ea0-953c-afc745495931",
  "tour_id": "08c786e1-19f8-4ffb-b850-c353c62185cc",
  "version": 2,
  "status": "draft",
  "trigger_type": "on_load",
  "target_path": "/additem*",
  "audience": { "show_once": true, "max_shows": 0, "only_new": false },
  "created_at": "2026-08-07T14:55:40.05Z"
}
```

`409`, если черновик уже есть — тогда клиент просто открывает существующий.

### `PATCH /v1/tours/{tourId}/draft` — изменить содержание черновика

Валидация здесь **не блокирует сохранение**: админ должен иметь возможность сохранить
незаконченную работу и вернуться к ней. Блокирует только публикация.

Request:

```json
{
  "trigger_type": "on_load",
  "target_path": "/additem/new*",
  "audience": { "show_once": true, "max_shows": 3, "only_new": false }
}
```

Response `200`: объект версии. `409`, если черновика нет.

### `POST /v1/tours/{tourId}/publish` — опубликовать черновик

Главная операция. В одной транзакции: блокировка тура `SELECT ... FOR UPDATE`, архивация
текущей опубликованной, промоушен черновика.

Блокировка не опциональна: без неё два одновременных нажатия «Опубликовать» оба проходят
проверку «черновик есть», и второе умирает на уникальном индексе сырой ошибкой драйвера.

Request: `none`

Response `200`:

```json
{
  "id": "c82c240c-2195-4647-86ac-415caf2788e0",
  "tour_id": "08c786e1-19f8-4ffb-b850-c353c62185cc",
  "version": 1,
  "status": "published",
  "trigger_type": "on_load",
  "target_path": "/additem*",
  "audience": { "show_once": true, "max_shows": 0, "only_new": false },
  "created_at": "2026-08-07T14:55:39.85Z",
  "published_at": "2026-08-07T14:55:39.95Z"
}
```

Ошибки: `409` — черновика нет; `422` — черновик не проходит валидацию:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Tour cannot be published",
    "details": [{ "path": "hints", "message": "a tour with no hints has nothing to show" }]
  }
}
```

Что проверяется: подсказок хотя бы одна; номера шагов идут подряд с 1 без дыр и дублей;
заголовок и текст непусты; `placement` из словаря; `selector` задан везде, кроме
`placement: center`; `target_path` непуст; `trigger_type` известен. Все проблемы
возвращаются разом — заставлять пересохранять ради следующей ошибки плохой размен.

### `POST /v1/tours/{tourId}/rollback` — откатиться к версии

Историю **не переписываем, а дополняем**: содержание указанной версии копируется в новую,
и она публикуется обычным путём. Если бы мы вернули статус старой строке, события до и
после отката слились бы в одну выборку, и цифры версии 5 перестали бы означать версию 5.

Request:

```json
{ "to_version_id": "c82c240c-2195-4647-86ac-415caf2788e0" }
```

Response `200`:

```json
{
  "id": "8176e13d-d474-447f-abf0-f5b82a0cdbf6",
  "tour_id": "08c786e1-19f8-4ffb-b850-c353c62185cc",
  "version": 3,
  "status": "published",
  "trigger_type": "on_load",
  "target_path": "/additem*",
  "audience": { "show_once": true, "max_shows": 0, "only_new": false },
  "created_at": "2026-08-07T14:55:40.15Z",
  "published_at": "2026-08-07T14:55:40.15Z"
}
```

`409`, если есть незакоммиченный черновик: молча выбросить несохранённую работу админа
хуже, чем отказать.

## Подсказки

Все операции адресуют **тур**, а работают с его черновиком — версия выводится из `tourId`,
так что вызывающему не надо знать, какую версию он редактирует. Попытка тронуть подсказку
опубликованной версии даёт `409` и на уровне приложения, и на уровне триггера в БД.

### `POST /v1/tours/{tourId}/hints` — добавить подсказку

Номер шага назначается сам: `max(step) + 1`.

Request:

```json
{
  "title": "Начните здесь",
  "content": "Нажмите, чтобы разместить объявление.",
  "selector": "[data-onboarding-id=post-ad-btn]",
  "placement": "bottom",
  "media_url": "",
  "spotlight": true,
  "required": false,
  "wait_for_selector": false,
  "input_placeholder": "",
  "expected_input": ""
}
```

- `placement` — `top` | `bottom` | `center` | `left` | `right` | `left-top` | `right-top`
- `selector` — обязателен для всего, кроме `center`: центрированная подсказка висит
  посреди экрана и якорь ей не нужен
- `wait_for_selector` — ждать появления элемента (в SPA DOM приходит асинхронно)

Response `201`:

```json
{
  "id": "87d259c5-d5b9-4e95-a36d-13e5b975212e",
  "tour_version_id": "c82c240c-2195-4647-86ac-415caf2788e0",
  "step": 1,
  "title": "Начните здесь",
  "content": "Нажмите, чтобы разместить объявление.",
  "selector": "[data-onboarding-id=post-ad-btn]",
  "placement": "bottom",
  "media_url": "",
  "spotlight": true,
  "required": false,
  "wait_for_selector": false,
  "input_placeholder": "",
  "expected_input": "",
  "created_at": "2026-08-07T14:55:39.88Z",
  "updated_at": "2026-08-07T14:55:39.88Z"
}
```

### `GET /v1/tours/{tourId}/hints` — подсказки черновика

Рабочий набор редактора, отсортирован по `step`.

Request: `none`

Response `200`: массив подсказок.

### `PATCH /v1/tours/{tourId}/hints/{hintId}` — изменить подсказку

`step` через эту ручку не меняется — порядок задаётся отдельной операцией.

Request: тело как в `POST`.

Response `200`: обновлённая подсказка. `409`, если подсказка принадлежит не черновику.

### `DELETE /v1/tours/{tourId}/hints/{hintId}` — удалить подсказку

Удаляет и **закрывает дыру** в нумерации в той же транзакции. Это не косметика: публикация
дыры не пропускает, так что удаление без пересчёта сделало бы тур непубликуемым с ошибкой
на подсказке, которую админ не трогал.

Request: `none`

Response `204`, без тела.

### `PUT /v1/tours/{tourId}/hints/order` — переупорядочить

Принимает **полный** список в новом порядке, а не «переставь одну»: результат однозначен,
и нет состояния, где клиент и сервер по-разному представляют себе вторую половину списка.
Все id резолвятся до первой записи, чтобы кривой id не оставил тур наполовину
перенумерованным.

Request:

```json
{ "hint_ids": ["dcaa2924-...", "40d189e7-..."] }
```

Response `200`: массив подсказок в новом порядке.

`400`, если список неполный или содержит чужой id.

## Рантайм (SDK)

### `POST /v1/resolve` — что показать пользователю

Единственный запрос, который SDK делает при инициализации. Возвращает **максимум один**
тур и **целиком**.

Целиком — потому что запрос за каждой подсказкой добавил бы 200–400 мс на каждый клик
(визуально — лаг), а обрыв сети рвал бы онбординг посередине. При отдаче целиком обрыв сети
ломает аналитику, но не сам онбординг.

Максимум один — потому что два оверлея на экране одновременно это сломанный UX. Конкуренция
разрешается по `priority DESC, created_at ASC`: детерминированно и настраивается из админки.

Request (заголовок `X-App-Key` обязателен):

```json
{
  "url": "https://demo.local/additem?cat=1",
  "subject_id": "anon_1",
  "session_id": "s1",
  "props": { "isNewUser": true, "adsCount": 0 }
}
```

- `subject_id` — `userId` хоста, если есть; иначе `anonId` из localStorage
- `props` — произвольные атрибуты пользователя от хост-приложения; по ним работает
  `audience`, и вычисляется он на бэке, потому что таргетинг, отданный в браузер, —
  это таргетинг, который в браузере перепишут

Response `200`:

```json
{
  "tour": {
    "id": "08c786e1-19f8-4ffb-b850-c353c62185cc",
    "app_id": "73d31e53-3a7b-48c0-93a9-36ec63ffbecd",
    "title": "Публикация объявления",
    "description": "Проводим нового пользователя до публикации",
    "enabled": true,
    "priority": 10,
    "created_at": "2026-08-07T14:55:39.85Z",
    "updated_at": "2026-08-07T14:55:39.93Z",
    "version_id": "c82c240c-2195-4647-86ac-415caf2788e0",
    "version": 1,
    "status": "published",
    "trigger_type": "on_load",
    "target_path": "/additem*",
    "audience": { "show_once": true, "max_shows": 0, "only_new": false },
    "hints": [ "...полный список подсказок..." ]
  },
  "tour_version_id": "c82c240c-2195-4647-86ac-415caf2788e0",
  "version": 1,
  "current_hint_id": "87d259c5-d5b9-4e95-a36d-13e5b975212e"
}
```

Response `204` — показывать нечего. **Это нормальный, ожидаемый ответ, а не ошибка**:
SDK работает на каждой загрузке страницы, а онбординга на большинстве страниц нет.

Порядок отбора: приложение по ключу и проверка `Origin` → туры с `enabled` и непустой
опубликованной версией → фильтр по `target_path` → фильтр по `audience` → первый
по приоритету → чтение/создание прогресса.

**Смена версии на лету.** Если у пользователя есть незавершённый прогресс по версии,
которая больше не опубликована, позиция **не переносится**: прогресс закрывается, и тур
начинается заново с первого шага актуальной версии. Подсказки новой версии — физически
другие строки с другими id, и подбор «эквивалента» породил бы события, не соответствующие
ничему, что кто-либо видел на экране.

### `POST /v1/events` — батч событий

Вызывается асинхронно и UI не блокирует. До 50 событий в батче.

Идемпотентность по `event_key`: SDK шлёт батчи с ретраями после обрыва сети, и без этого
каждый ретрай удваивал бы метрики. Дубликат не двигает прогресс повторно — иначе
идемпотентность вставки ничего бы не стоила.

Кривое событие **не роняет батч**: оно попадает в `rejected`, остальные 49 записываются.
Именно поэтому словарь типов проверяется в коде, а не `CHECK`-ом в БД — нарушение
constraint откатило бы всю транзакцию.

Request (заголовок `X-App-Key` обязателен):

```json
{
  "subject_id": "anon_1",
  "session_id": "s1",
  "events": [
    {
      "event_key": "b1e7a0c2-19f4-4a3d-9c11-2f8e5a6d0b73",
      "type": "hint_shown",
      "tour_id": "08c786e1-19f8-4ffb-b850-c353c62185cc",
      "tour_version_id": "c82c240c-2195-4647-86ac-415caf2788e0",
      "hint_id": "87d259c5-d5b9-4e95-a36d-13e5b975212e",
      "occurred_at": "2026-08-07T14:55:40.10Z",
      "payload": {}
    }
  ]
}
```

Словарь `type`:

| type | hint_id | Смысл |
|---|---|---|
| `tour_started` | нет | Тур начат, показан первый шаг |
| `hint_shown` | есть | Подсказка отрисована на экране |
| `hint_completed` | есть | Пользователь сделал нужное действие |
| `hint_skipped` | есть | Шаг пропущен |
| `selector_missing` | есть | Элемент не найден. **Сигнал «тур сломан»** |
| `tour_completed` | нет | Пройден последний шаг |
| `tour_dismissed` | нет | Закрыт крестиком |
| `goal_reached` | нет | Достигнут бизнес-результат |

**Что проверяется у каждого события.** Идентификаторы в теле — это клиентский ввод, и ниже
их никто не перепроверяет: у `tour_events.tour_id` внешнего ключа нет вовсе, а ключи на
`tour_version_id` и `hint_id` глобальные и не связывают событие с приложением, которое его
прислало. Поэтому связи проверяются здесь:

| Причина отказа | Когда |
|---|---|
| `event_key is required` | Пустой `event_key` — без него ретрай удвоит метрики |
| `unknown event type` | Типа нет в словаре |
| `tour_version_id is required` | Не указана версия |
| `version not found` | Версии не существует |
| `tour version belongs to another application` | Версия принадлежит чужому приложению |
| `tour_id is required` | Пустой `tour_id` |
| `tour version does not belong to the specified tour` | Версия не из этого тура |
| `hint does not belong to the specified tour version` | Подсказка не из этой версии |
| `hint id must be set for hint-level events...` | `hint_id` не соответствует уровню события |

Версия резолвится один раз на батч, так что пятьдесят событий об одной версии стоят
два запроса, а не сто.

Устаревшие события принимаются в лог, но **прогресс не двигают**: `hint_completed`
и `tour_completed` применяются только к той версии, на которой пользователь сейчас
находится. Иначе вкладка, открытая во время публикации, отметила бы человека прошедшим
версию, которой он не видел.

`goal_reached` учитывается **отдельно** от `tour_completed`. Пользователь может прокликать
все подсказки и не опубликовать объявление — или опубликовать, закрыв тур на середине.
Разница между этими метриками и есть ответ на вопрос «помогает тур или его вежливо кликают
насквозь». Слить их значит заставить метрику измерять саму себя.

Response `202`:

```json
{ "accepted": 7, "duplicates": 0, "rejected": 0 }
```

При повторной отправке того же батча:

```json
{ "accepted": 0, "duplicates": 7, "rejected": 0 }
```

При кривом событии в батче:

```json
{ "accepted": 1, "duplicates": 0, "rejected": 1, "errors": ["unknown event type"] }
```

## Аналитика

### `GET /v1/tours/{tourId}/analytics` — воронка и сводка

Период фильтруется по `received_at`, а не по `occurred_at`: часы клиента могут быть
сдвинуты на часы, и отчёт «за вчера», построенный на них, тихо захватит или потеряет
не те сессии.

Request:

`versionId` - uuid - версия; по умолчанию опубликованная
`from` - string - начало периода, RFC3339; по умолчанию 30 дней назад
`to` - string - конец периода, RFC3339; по умолчанию сейчас

Response `200`:

```json
{
  "tour_id": "08c786e1-19f8-4ffb-b850-c353c62185cc",
  "tour_version_id": "c82c240c-2195-4647-86ac-415caf2788e0",
  "version": 1,
  "from": "2026-07-08T14:50:50Z",
  "to": "2026-08-07T14:50:50Z",
  "totals": {
    "started": 2,
    "completed": 1,
    "dismissed": 0,
    "goal_reached": 1,
    "completion_rate": 0.5,
    "goal_rate": 0.5
  },
  "funnel": [
    {
      "step": 1,
      "hint_id": "40d189e7-a81f-4e91-bbbe-820ae20632f7",
      "title": "Начните здесь",
      "shown": 1, "completed": 1, "skipped": 0,
      "selector_missing": 0, "dropoff": 0
    },
    {
      "step": 2,
      "hint_id": "dcaa2924-2139-473d-9ed8-36c62eebcf72",
      "title": "Выберите категорию",
      "shown": 1, "completed": 0, "skipped": 0,
      "selector_missing": 1, "dropoff": 1
    }
  ],
  "broken_selectors": ["dcaa2924-2139-473d-9ed8-36c62eebcf72"]
}
```

Счёт идёт по `COUNT(DISTINCT subject_id)`, а не по числу событий: пользователь, вернувшийся
на шаг дважды, — один человек, воронка меряет людей.

Подсказка, до которой никто не дошёл, всё равно присутствует в `funnel` с нулями — это
ровно та строка, которую админу нужно увидеть.

`broken_selectors` — подсказки, чей якорь не нашёлся на странице. Не отладочный лог,
а продуктовая фича: без неё онбординг молча перестаёт работать после того, как фронтендер
хоста переписал компонент, и никто об этом не узнаёт.

## Служебные

### `GET /v1/health` — проверка живости

Пингует БД, а не только процесс: процесс, который отвечает при недоступной базе, —
именно то состояние, ради которого healthcheck и существует. Аутентификация не нужна.

Request: `none`

Response `200`:

```json
{ "status": "ok", "db": "ok" }
```

Response `503`:

```json
{ "status": "degraded", "db": "down" }
```

## Запуск

```bash
docker compose up -d --build
```

Поднимается три контейнера:

| Сервис | Порт | Что это |
|---|---|---|
| `postgres` | 5432 | БД |
| `onboarding` | 8080 | Платформа онбординга |
| `demo` | 8081 | Тестовый классифайд, на котором показывается онбординг |

Онбординг — отдельный бинарь и отдельный контейнер от демо-сайта намеренно: платформа это
продукт, механизм, подключаемый к любому веб-приложению, а классифайд — один из её
потребителей. В одном процессе эта граница стала бы невидимой.

Миграции встроены в бинарь и применяются на старте, до первого запроса: наполовину
мигрированная база, которая обслуживает трафик, хуже простоя — она падает только на части
строк.

Конфиг читается из `/run/secrets/cluer.yml`; в compose туда монтируется `deploy/onboarding.yml`.

### Быстрая проверка

```bash
curl -s localhost:8080/v1/health

APP=$(curl -s -X POST localhost:8080/v1/apps \
  -H 'Content-Type: application/json' \
  -d '{"name":"Demo","allowed_origins":["http://localhost:3000"]}')
echo "$APP"
```

Дальше — `POST /v1/tours?appId=...`, две подсказки, `POST /publish`, `POST /resolve`.

### Swagger

```bash
swag init -g cmd/onboarding/main.go -d ./ --parseDependency --parseInternal -o ./docs
```

**Внимание:** `swag init` вычищает каталог `docs/` целиком. Держать там что-либо написанное
руками нельзя — поэтому этот файл и `onboarding-flows.md` лежат в корне.
