# Онбординг — флоу и пользовательские сценарии

Справочник по ручкам — в [onboarding-api.md](onboarding-api.md). Здесь другое: как система
живёт во времени, в каком порядке всё вызывается и в какие состояния переходит.

Все переходы ниже проверены на живом стенде, а не выведены из кода.

---

## 1. Три роли

| Кто | Что делает | Чем ходит |
|---|---|---|
| **Админка** | Собирает тур, публикует, смотрит воронку | Открытые ручки `/v1/tours`, `/v1/apps` |
| **SDK** | Спрашивает что показать, рисует подсказки, шлёт события | `/v1/resolve`, `/v1/events` с `X-App-Key` |
| **Бэк** | Хранит версии, решает кому что показать, считает воронку | — |

Цикл замкнут: админ публикует → бэк резолвит → SDK показывает → события возвращаются →
админ видит воронку и правит → новая версия.

**SDK пока нет.** Ниже он описан как контракт: что бэк от него ждёт и что ему обещает.
Всё, что помечено «SDK», сейчас воспроизводится курлом.

---

## 2. Жизненный цикл версии

```
                    POST /tours
                        │
                        ▼
                   ┌─────────┐
                   │  draft  │◄──────┐
                   │   v1    │       │ POST /tours/{id}/draft
                   └────┬────┘       │ (копия published + её подсказок)
                        │            │
          POST /publish │            │
                        ▼            │
                   ┌───────────┐     │
                   │ published │─────┘
                   │    v1     │
                   └─────┬─────┘
                         │ следующий POST /publish
                         ▼
                   ┌──────────┐
                   │ archived │  (терминальное)
                   │    v1    │
                   └──────────┘
```

Правила, которые держит БД, а не договорённость:

- у тура **максимум одна** `published` и **максимум один** `draft` — частичные уникальные индексы;
- тело версии, вышедшей из `draft`, **не меняется ничем**, включая прямой SQL — триггеры
  `tour_versions_immutability` и `hints_immutability`;
- подсказки принадлежат версии, поэтому заморозка распространяется и на них.

Тур сам по себе статуса не имеет. «Что сейчас живёт» — это версия со статусом `published`,
и она выводится запросом, а не хранится указателем.

## 3. Админские сценарии

### A1. Завести всё с нуля

```
POST /v1/apps                        → app_id + public_key
POST /v1/tours?appId=...             → tour_id, автоматически draft v1
POST /v1/tours/{id}/hints            → подсказка, step=1
POST /v1/tours/{id}/hints            → подсказка, step=2
PATCH /v1/tours/{id}  {"enabled":true}
POST /v1/tours/{id}/publish          → v1 становится published
```

Что важно в этой цепочке:

- **Тур создаётся сразу с черновиком.** Тур без версии — состояние, которое редактору
  нечем отрисовать, поэтому оно недостижимо даже на промежуток между двумя запросами.
- **`enabled` и публикация — независимые вещи.** Опубликованный, но выключенный тур
  не резолвится. Это позволяет подготовить тур заранее и включить в нужный момент.
- **`step` назначает бэк** (`max+1`), клиент его не передаёт.

### A2. Отредактировать живой тур

Опубликованную версию править нельзя — ни через API, ни через SQL. Правка это форк:

```
POST  /v1/tours/{id}/draft           → 201, draft v2 = копия v1 + копии её подсказок
PATCH /v1/tours/{id}/hints/{hintId}  → правим подсказки v2
PATCH /v1/tours/{id}/draft           → правим таргетинг v2
POST  /v1/tours/{id}/publish         → v1 → archived, v2 → published
```

Пока v2 в черновике, **живой пользователь продолжает видеть v1** — публикация атомарна.

`409` на `POST /draft`, если черновик уже есть: клиент просто открывает существующий.

### A3. Публикация не прошла

Валидация при сохранении черновика **не блокирует** — админ должен уметь сохранить
незаконченную работу. Это относится и к подсказкам: `POST /hints` с телом `{}` создаёт
пустую подсказку и отдаёт `201`, `PATCH /hints/{hintId}` разрешает обнулить её обратно.
Отвергается на месте ровно одна вещь — неизвестный `trigger_type` в `PATCH /draft` (`400`),
потому что это не «ещё не заполнено», а значение вне словаря.

Всё остальное блокирует только публикация — единственное место, где черновик проверяется
целиком:

```
POST /v1/tours/{id}/publish
→ 422
{
  "error": "tour cannot be published: hints[1].content: must not be empty; hints[1].selector: required unless placement is center",
  "message": "Tour cannot be published"
}
```

Тело ошибки плоское: `message` — формулировка для интерфейса, `error` — перечень проблем
в форме `путь: причина`, склеенный через `; `. Индексы с нуля, `hints[1]` — вторая подсказка.

Все проблемы приходят разом, а не по одной за запрос. Иначе одна опечатка в редакторе
кладёт онбординг в проде, и узнаёте вы об этом от пользователей.

### A4. Откатиться на предыдущую версию

```
POST /v1/tours/{id}/rollback  {"to_version_id": "<id версии 1>"}
```

Историю **не переписываем, а дополняем**: содержание v1 копируется в v3, и v3 публикуется.
v1 остаётся `archived`.

```
до:    v1 archived   v2 published
после: v1 archived   v2 archived   v3 published (копия v1)
```

Если бы мы просто вернули статус старой строке, события до и после отката слились бы
в одну выборку и цифры v1 перестали бы означать v1.

`409`, если есть незакоммиченный черновик: молча выбросить несохранённую работу админа
хуже, чем отказать.

### A5. Выключить временно или удалить

| Хочу | Что делать | Что происходит |
|---|---|---|
| Остановить показы, потом вернуть | `PATCH {"enabled": false}` | Резолв даёт `204`. Версия не меняется, статистика цела |
| Убрать совсем | `DELETE /v1/tours/{id}` | `archived_at`, тур исчезает из списка и резолва |

Проверено: после `enabled: false → true` резолвится **та же версия**, новая не появляется.
Рубильник — это управление, а не редакция; плодить из-за него версию значит рвать
статистику на ровном месте.

Жёсткого удаления нет и не будет: `ON DELETE RESTRICT` со стороны событий его не пропустит.
Это осознанно — удалённый тур унёс бы с собой историю аналитики.

## 4. Пользовательские сценарии

### U1. Первый заход на страницу

```
SDK → POST /v1/resolve
      { "url": "https://site/additem?cat=1",
        "subject_id": "anon_8f3d", "session_id": "sess_2b91",
        "props": { "isNewUser": true } }
```

Бэк отбирает по шагам:

1. приложение по `X-App-Key`, проверка `Origin`;
2. туры этого приложения с `enabled` и непустой `published`-версией;
3. фильтр по `target_path` (glob против `path + query`);
4. фильтр по `audience` относительно `props` и прогресса;
5. первый по `priority DESC, created_at ASC`;
6. чтение или создание прогресса.

Два исхода:

- **`200`** — тур целиком плюс `current_hint_id`. При первом заходе указатель на первый шаг.
- **`204`** — показывать нечего. Это **нормальный ответ**, а не ошибка: SDK работает
  на каждой загрузке страницы, а онбординга на большинстве страниц нет.

`subject_id` — `userId` хоста, если пользователь авторизован, иначе `anonId` из localStorage.

### U2. Прохождение

SDK получил тур целиком и дальше работает без сети. Он **реактивен, а не императивен**:
не ведёт пользователя навигацией, а ждёт, пока условия шага станут истинными, и рисует
подсказку. Ушёл пользователь в сторону — молчит, вернулся — подсказка появилась снова.

События идут батчами, асинхронно, UI не блокируют:

```
tour_started   → бэк: ничего не меняет в прогрессе (прогресс создал resolve)
hint_shown     → бэк: ничего
hint_completed → бэк: current_hint_id сдвигается на следующий шаг версии
hint_skipped   → бэк: ничего
tour_completed → бэк: status = completed, finished_at = now()
tour_dismissed → бэк: status = dismissed, finished_at = now()
goal_reached   → бэк: прогресс НЕ трогает
```

`goal_reached` намеренно не двигает прогресс: бизнес-результат — не шаг тура.

### U3. Вернулся позже или с другого устройства

Прогресс лежит на бэке, а не в localStorage. localStorage чистится, не переживает смену
устройства, и ему нельзя доверять — пользователь может подделать «я уже прошёл».

```
resolve (сессия s1) → current_hint_id = h1
POST /events hint_completed h1
resolve (сессия s2) → current_hint_id = h2   ← прогресс пережил новую сессию
```

Проверено. На фронте localStorage допустим только как кэш для мгновенной отрисовки
до ответа сети.

### U4. Закрыл крестиком

`tour_dismissed` → `status = dismissed`. Если у тура `audience.show_once = true`,
следующий резолв для этого subject вернёт `204`.

`dismissed` хранится отдельно от `completed` не для симметрии: «закрыл на втором шаге» —
важный негативный сигнал для продуктовой команды, и сливать его с «дошёл до конца» значит
потерять единственное место, где он виден.

### U5. Версия сменилась посреди прохождения

Самый неочевидный сценарий и главная причина, по которой прогресс хранит `tour_version_id`.

```
u1 проходит v1, дошёл до второго шага (current_hint_id = h2 из v1)
   админ публикует v2
u1 заходит снова
   → resolve отдаёт v2
   → current_hint_id указывает на ПЕРВЫЙ шаг v2, а не на h2
```

Позиция **не переносится**. Подсказки v2 — физически другие строки с другими UUID;
подсказки с идентификатором `h2` в новой версии просто нет. Подобрать «эквивалент»
означало бы породить события, не соответствующие ничему, что кто-либо видел на экране,
и воронка перестала бы быть достоверной. Лучше честно начать заново.

Строка прогресса при этом **не дублируется**: у subject остаётся одна запись на тур,
в ней меняются `tour_version_id` и указатель, а `shows_count` продолжает расти.
Проверено: после трёх резолвов через смену версии — одна строка, `shows_count = 3`.

### U6. Обрыв сети

Тур отдан целиком одним ответом, поэтому обрыв сети **ломает аналитику, но не онбординг** —
пользователь продолжает проходить его до конца.

Когда сеть вернулась, SDK повторяет батч. Повтор безопасен: вставка идёт
`ON CONFLICT (app_id, event_key) DO NOTHING`, и `event_key` генерирует клиент.

```
первая отправка:  {"accepted": 6, "duplicates": 0, "rejected": 0}
повтор того же:   {"accepted": 0, "duplicates": 6, "rejected": 0}
```

Дубликат не двигает прогресс повторно — иначе идемпотентность вставки ничего бы не стоила.

Отдельный случай — вкладка, пережившая публикацию. Её события про старую версию
**принимаются в лог** (это настоящие данные о той версии), но прогресс не трогают:
`applyProgress` бьёт только по той версии, на которой пользователь сейчас. Проверено —
после досылки `hint_completed(v1)` и `tour_completed(v1)` строка прогресса остаётся
`in_progress` на v2, а `current_hint_id` продолжает указывать на подсказку v2.

Без этой привязки старая вкладка отметила бы человека прошедшим версию, которой он
не видел, и при `show_once` он потерял бы онбординг навсегда.

SDK должен слать батч по таймеру (~2 с) и через `navigator.sendBeacon` на `visibilitychange`,
чтобы не терять события при закрытии вкладки.

### U7. Селектор не нашёлся

Вёрстка хоста изменилась, элемент под `#category` больше не существует. SDK ждёт
`wait_for_selector` и, не дождавшись, шлёт `selector_missing`.

Это **не отладочный лог, а продуктовая фича**. Событие попадает в аналитику, и подсказка
всплывает в `broken_selectors`:

```json
"funnel": [
  { "step": 2, "hint_id": "dcaa...", "title": "Выберите категорию",
    "shown": 1, "completed": 0, "selector_missing": 1, "dropoff": 1 }
],
"broken_selectors": ["dcaa2924-2139-473d-9ed8-36c62eebcf72"]
```

Без этого события онбординг молча перестаёт работать, и никто не узнаёт.

### U8. Под страницу подходит несколько туров

Возвращается **ровно один**: два оверлея на экране одновременно — сломанный UX.

Разрешение по `priority DESC, created_at ASC` — детерминированно и настраивается
из админки. Проверено: тур с `priority=99` выигрывает у тура с `priority=10`;
после архивации первого резолв возвращается ко второму.

## 5. Аналитическая петля

```
воронка показала отвал на шаге 2
        │
        ▼
POST /tours/{id}/draft          форкнули черновик
PATCH .../hints/{hintId}        переписали текст шага 2
POST /tours/{id}/publish        v2 в проде
        │
        ▼
GET /tours/{id}/analytics?versionId=<v1>   старые цифры
GET /tours/{id}/analytics?versionId=<v2>   новые цифры
```

Сравнение возможно **только потому**, что версия иммутабельна и каждое событие несёт
`tour_version_id`. Если бы текст можно было поправить на месте, один `UPDATE` задним числом
обесценил бы всю накопленную статистику: цифры относились бы к одному тексту, а в базе
лежал бы другой, и различить их было бы нечем.

Две метрики, которые нельзя сливать:

| Метрика | Что означает |
|---|---|
| `completion_rate` | Доля дошедших до последнего шага |
| `goal_rate` | Доля достигших бизнес-результата |

Пользователь может прокликать все подсказки и не опубликовать объявление — или опубликовать,
закрыв тур на середине. Разница между этими числами и есть ответ на вопрос «помогает тур
или его вежливо кликают насквозь».

Период фильтруется по `received_at`, а не `occurred_at`: часы клиента могут быть сдвинуты
на часы, и отчёт «за вчера» на них тихо захватил бы не те сессии.

Считается `COUNT(DISTINCT subject_id)`: вернувшийся на шаг дважды — один человек,
воронка меряет людей, а не показы.

## 6. Граница ответственности

| Решает бэк | Решает SDK |
|---|---|
| Какой тур показать этому пользователю | Когда именно отрисовать подсказку |
| Кому показывать (`audience`) | Нашёлся ли элемент в DOM |
| С какого шага начать | Сработало ли условие перехода |
| Считать ли тур пройденным | Как выглядит подсказка |

Таргетинг вычисляется **на бэке**: логику «кому показывать», отданную в браузер,
в браузере и перепишут.

Переходы между шагами бэк **не диктует**, а только регистрирует. Логика «какой шаг
следующий» уже в туре, полученном на старте. Запрос за каждым шагом добавил бы 200–400 мс
на каждый клик — визуально это лаг.

## 7. Чего в сценариях пока нет

- **SDK** — в `frontend/` уже есть React-админка и демо-классифайд, и админка ходит
  в те же открытые ручки `/v1/tours`. Рантайма, который ходит в `/resolve` и `/events`,
  среди них нет: демо берёт подсказки из `GET /v1/tours/published`. Всё, что помечено
  «SDK», по-прежнему воспроизводится курлом.
- **PDF-отчёт** — таблица `reports` создана, ручки нет.
- **Ветвление шагов** — только линейные туры.
- **A/B двух версий одного тура** — мешает инвариант «одна published на тур».
  Потребует отдельного механизма раскатки, а не ослабления инварианта.
- **Авторизация** — админские ручки открыты, все считаются одним замоканным админом.
