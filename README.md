
## Описание проекта
Cluer - это централизованная платформа для создания, управления и аналитики пошаговых сценариев онбординга (tours, гайды, подсказки) для веб-сервисов.
Платформа решает проблему сложного и дорогого внедрения онбординга, позволяя создавать интерактивные подсказки без участия разработчиков.

Проект разворачивается через Docker Compose — локально или на сервере. Инструкция ниже: сначала запуск, затем три шага первичной настройки, которые нужно сделать один раз на пустой инсталляции.

Платформа состоит из трех ключевых компонентов:
-  Admin Panel (Frontend) — визуальный конструктор гайдов с возможностью выбора DOM-элементов и управления версиями (Draft/Published).
-  Backend (API + Storage) — серверная часть на Go с PostgreSQL, отвечающая за хранение сценариев, строгое версионирование и агрегацию событий.
-  SDK (Widget) — клиентский рантайм, который встраивается в страницы сервиса (Классифайдс), отслеживает триггеры и показывает подсказки.

## Инструкция по запуску:
Для запуска достаточно Docker и Docker Compose. Go (1.26+) и Node.js (22+) нужны только для разработки без контейнеров.
1) Клонирование репозитория
   git clone https://github.com/Vanady39/cluer.git && cd cluer
2) Создание конфигурации из шаблона
   cp sample_config.yml deploy/cluer.yml
   Файла нет в репозитории, и без него compose создаст на его месте каталог, а сервисы упадут на чтении конфига. Пароль базы туда вписывать не нужно — он приходит из .env.
3) Создание .env из шаблона
   cp .env.example .env
   Заполняются три секрета — AUTHENTIK_SECRET_KEY, AUTHENTIK_PG_PASS и CLUER_POSTGRES_PASSWORD. Генерируются на месте (команды в комментариях шаблона), переносить их с другой машины нельзя. Без них compose откажется стартовать с явным сообщением. Адреса для запуска на localhost можно оставить пустыми: docker-compose.yml подставит рабочие значения по умолчанию.
4) docker compose up -d --build
   Сборка идет параллельно и требует около 2 ГБ свободной памяти: одновременно компилируются три Go-сервиса, следом собирается фронтенд. На машине с 2 ГБ и без свопа сборку убьет OOM-killer — признаки описаны в разделе про сервер.
5) Что поднимается и на каких портах:
   - http://localhost:5173 — тестовый сайт классифайда (он же точка входа SDK)
   - http://localhost:5173/admin/scenarios — админка онбординга
   - http://localhost:9000 — Authentik, провайдер аутентификации
   - http://localhost:5173/v1 и http://localhost:5173/demo/v1 — API онбординга и демо через прокси фронтенда
   - 127.0.0.1:8080 и 127.0.0.1:8081 — те же API напрямую, только с самой машины: наружу они не публикуются, браузер ходит в них через фронтенд
   - 127.0.0.1:5432 — PostgreSQL, пользователь cluer, пароль из CLUER_POSTGRES_PASSWORD в .env

Миграции накатывает отдельный одноразовый контейнер migrate: он отрабатывает до старта onboarding и demo, которые ждут его успешного завершения. Отдельная команда не нужна.
Конфигурация одна на всё: deploy/cluer.yml. Файл не в репозитории — он копируется из sample_config.yml и несет реальные пароль базы и issuer. Его читают две системы, каждая берет свою часть и игнорирует чужую:
- Go-сервисы (migrate, onboarding, demo) — секции server/postgres/oidc/logger, файл монтируется как /run/secrets/cluer.yml;
- Authentik — секции version/metadata/entries, это blueprint. Монтируется в authentik-server и authentik-worker как /blueprints/custom/cluer.yaml и применяется автоматически при старте, так что группа cluer-admins, OAuth2-провайдер и приложение в Authentik заводятся сами.

Переменные окружения с префиксом CLUER_ перекрывают значения из файла: точка в пути ключа становится подчеркиванием (postgres.address → CLUER_POSTGRES_ADDRESS). Одна тонкость: viper подставляет переменную только для ключа, который уже есть в файле. Поэтому в секции postgres оставлена строка `password: ""` — она пустая, но без нее CLUER_POSTGRES_PASSWORD будет молча проигнорирован.

Swagger UI собирается только с тегом debug (go build -tags debug), в обычной сборке ручка /swagger отключена.

## Первый запуск: три шага руками

Стек поднимается сам, но пустая инсталляция не знает ни одного пользователя, а онбординг — ни одного приложения. Эти три шага делаются один раз, по порядку: каждый следующий опирается на предыдущий.

Перед началом убедитесь, что blueprint применился — именно он создает группу, в которую предстоит добавлять пользователя:

```
docker compose logs authentik-worker | grep apply_blueprint
```

Ожидается `Task finished ... state: SUCCESS`. Authentik стартует не мгновенно, у него start_period 60 секунд.

### Шаг 1. Администратор Authentik

Открыть в браузере `http://<адрес>:9000/if/flow/initial-setup/` и задать email и пароль для встроенного пользователя `akadmin`.

Форма одноразовая: после первого прохождения она больше не откроется. Если пропустить шаг и сразу пойти в админку, войти будет некем.

### Шаг 2. Членство в группе cluer-admins

Войти в `http://<адрес>:9000/if/admin/` и пройти: **Directory → Groups → cluer-admins → вкладка Users → Add existing user → akadmin**.

Группа уже создана blueprint'ом, но она пустая. Без этого шага вход в админку пройдет успешно, а все админские ручки вернут 403: токен будет валидным, но нужной группы в claim `groups` не окажется. Это самый частый способ решить, что «ничего не работает».

### Шаг 3. Ключ приложения для SDK

SDK подписывается ключом приложения из таблицы `apps`. Отдельной страницы в админке для этого нет, приложение создается через API.

Залогиниться в `http://<адрес>:5173/admin/scenarios`, затем в консоли браузера (F12) скопировать токен в буфер:

```
copy(JSON.parse(Object.entries(localStorage).find(([k]) => k.startsWith('oidc.user:'))[1]).id_token)
```

Создать приложение, подставив токен:

```
TOKEN='<вставить>'
curl -s -X POST http://<адрес>:5173/v1/apps -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"name":"cluer-demo"}'
```

Запрос идет через порт фронтенда, а не через 8080: порт онбординга слушает только loopback, наружу он не публикуется.

В ответе будет `public_key` вида `pk_<uuid>` — ключ генерирует сервер, задавать его не нужно. Вписать значение в .env как `VITE_CLUER_APP_KEY` и пересобрать фронтенд, потому что Vite вшивает переменные в бандл на этапе сборки:

```
docker compose up -d --build frontend
```

Пока ключа нет, сайт и админка работают — не подтягиваются только сценарии SDK, так что шаг можно отложить.

## Развертывание на сервере
Значения по умолчанию рассчитаны на браузер, запущенный на той же машине. Для сервера в .env задаются два адреса — оба такие, как их видит браузер пользователя:
- CLUER_OIDC_ISSUER — issuer Authentik, например http://203.0.113.10:9000/application/o/cluer/. Одна переменная и для проверки токенов в Go-сервисах, и для сборки фронтенда, поэтому разъехаться они не могут. Authentik строит issuer из заголовка Host, так что значение должно совпадать с тем, как к нему обращаются, вместе с завершающим слэшем.
- CLUER_REDIRECT_URI — куда Authentik возвращает браузер после логина, например http://203.0.113.10:5173/callback. Подставляется в blueprint через тег !Env и сверяется строго.

Фронтенд вшивает issuer в бандл на этапе сборки, поэтому после правки .env нужен docker compose up -d --build frontend, а не рестарт.

Наружу публикуются только два порта: 5173 (фронтенд) и 9000 (Authentik, на него браузер уходит при логине). Порты Postgres, онбординга и демо привязаны к 127.0.0.1 — снаружи они недоступны, а браузер обращается к API через прокси фронтенда. Учтите, что ufw для docker-портов бесполезен: docker пишет правила DNAT в PREROUTING, трафик идет через FORWARD и до INPUT-правил ufw не доходит. Закрывает порт именно привязка адреса в docker-compose.yml, а не фаервол на хосте. Проверять закрытость нужно с другой машины (`nc -zv <IP> 5432`) — с самого сервера порт откликнется в любом случае.

### Про http и вход в админку

Вход работает по http, но не сам по себе. Библиотека авторизации считает PKCE-challenge через `crypto.subtle`, а браузер отдает его только в secure context — по https или на localhost. Для http на IP в проекте есть полифилл `frontend/src/Utils/insecureContextCrypto.ts`: он подставляет `crypto.subtle.digest` и `crypto.randomUUID`, когда браузер их не дает, и ничего не делает, когда дает. PKCE при этом настоящий, S256 — протокол не ослаблен.

Ослаблен транспорт: по http токен и код авторизации идут открытым текстом и доступны любому на пути. Для демо-стенда это осознанный размен, для чего-то большего нужен https. Дешевле всего он получается через сервис вида sslip.io: адрес `<IP>.sslip.io` резолвится в ваш IP без покупки домена, и на него выдается настоящий сертификат Let's Encrypt.

### Память при сборке

Сборка на сервере — самая тяжелая операция за все время жизни стека: параллельно компилируются три Go-сервиса, затем vite собирает фронтенд. Нужно около 2 ГБ свободной памяти и 10–15 ГБ диска.

Признак нехватки: `kswapd0` в топе процессов, `Killed` в выводе, код возврата 137. Лечится свопом:

```
sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
```

Чтобы своп пережил перезагрузку, его нужно прописать в /etc/fstab. Дополнительно помогает сборка по одному сервису за раз:

```
COMPOSE_PARALLEL_LIMIT=1 docker compose build
```

## Пользовательский путь и точки входа
Онбординг нужен там, где пользователь классифайда чаще всего останавливается, не дойдя до целевого действия. В демо-классифайде реализованы три экрана, и подсказки рассчитаны на них:
- Размещение объявления (/addItem) — основная точка входа. Здесь пользователь впервые встречает форму с категориями, городом и загрузкой фото, и именно тут теряется больше всего людей: непонятно, какие поля обязательны и что произойдет после публикации. Сценарий ведет по форме шаг за шагом до кнопки публикации.
- Лента и поиск (/) — вторая точка входа. Новый пользователь не знает про фильтры и выбор города, поэтому получает нерелевантную выдачу и уходит. Подсказки показывают, как сузить поиск.
- Профиль (/profile) — точка входа для возвращающихся пользователей, где объясняется, где искать свои объявления и сообщения.

Сценарий описывается администратором в админке: тур привязывается к target_path, шаги задаются CSS-селекторами якорей, для каждого шага выбирается расположение подсказки и подсветка (spotlight). Правила показа задаются аудиторией версии: show_once, max_shows, only_new. Тип триггера определяет момент запуска: on_load, delay, exit_intent или manual (вызов window.startOnboarding из кода сервиса).

## API
Все ручки живут под /v1. Рантайм-ручки требуют заголовок X-App-Key. Поле allowed_origins у приложения в схеме есть и заполняется, но пока не проверяется: CORS-мидлварь отражает любой присланный Origin.

Runtime (для SDK):
- POST /v1/resolve — получить опубликованный сценарий для текущего пути
- POST /v1/events — принять батч событий прохождения (идемпотентно по event_key)

Админка:
- POST /v1/apps, GET /v1/apps — регистрация приложения и выдача публичного ключа
- POST /v1/tours, GET /v1/tours, GET /v1/tours/published — создание и списки туров
- GET /v1/tours/{tourId}, PATCH /v1/tours/{tourId}, DELETE /v1/tours/{tourId} — карточка, метаданные, архивация
- GET /v1/tours/{tourId}/versions, GET /v1/versions/{versionId} — история версий
- POST /v1/tours/{tourId}/draft, PATCH /v1/tours/{tourId}/draft — работа с черновиком
- POST /v1/tours/{tourId}/publish, POST /v1/tours/{tourId}/rollback — публикация и откат
- POST/GET /v1/tours/{tourId}/hints, PUT /v1/tours/{tourId}/hints/order — подсказки и их порядок
- PATCH/DELETE /v1/tours/{tourId}/hints/{hintId} — изменение и удаление подсказки
- GET /v1/tours/{tourId}/analytics — воронка и агрегаты по версии за период
- GET /v1/users/me — администратор, за которым пришел токен (subject, профиль, группы)

Все перечисленные выше ручки требуют `Authorization: Bearer <id_token>`. Исключения — GET /v1/health и рантаймовые POST /v1/resolve, POST /v1/events: последние аутентифицируются ключом приложения в заголовке X-App-Key.

Демо-классифайд (отдельный сервис, наружу отдается через /demo/v1 на фронтенде):
- GET /v1/listings — лента объявлений, публичная: витрину смотрят и неаутентифицированные посетители
- GET /v1/users/me — посетитель, за которым пришел токен (subject, профиль). Требует `Authorization: Bearer <id_token>`, без токена 401. Групп не проверяет: на витрине любой аутентифицированный пользователь провайдера — валидный пользователь

## Стек технологий
- Backend: Go 1.26+ (Gin), pgx (Postgres driver), zerolog, viper, golang-migrate, swaggo (Swagger)
- Storage: PostgreSQL (реляционная схема, триггеры иммутабельности, частичные уникальные индексы, JSONB для payload событий)
- Frontend: React 19, TypeScript(~6.0) (Vite, Ant Design, Redux Toolkit, React Query, react-router-dom, ESLint, Sass)
- SDK: React/TypeScript рантайм (TourRunner.tsx) — polling-based selector detection (setInterval + querySelector)
- Auth: Authentik (OIDC-провайдер в том же compose), authorization code + PKCE на фронтенде (oidc-client-ts), проверка id_token и групп на бэкенде
- Integration & security: window.postMessage for Builder isolation, X-App-Key header (app identifier)
- Dev/tools: Docker, Docker Compose, GitHub Actions (CI), golangci-lint, ESLint, go modules, npm, migrations (golang-migrate)

## Почему PostgreSQL
База выбрана под главное требование продукта: аналитика не должна ломаться при правках сценария. Отсюда нужны жесткие инварианты, которые дешевле держать в СУБД, чем в коде.
- Частичные уникальные индексы гарантируют, что у тура есть максимум один Draft и максимум одна Published версия. В документной БД это пришлось бы поддерживать транзакциями в приложении.
- Триггеры замораживают опубликованные версии и их подсказки: отредактировать то, что уже видели пользователи, физически нельзя.
- Внешние ключи связывают события с конкретной версией и подсказкой, поэтому воронка всегда считается по тому тексту, который пользователь реально видел.
- UNIQUE (app_id, event_key) делает прием событий идемпотентным: повторная отправка батча не задваивает метрики.
- JSONB используется точечно, для payload событий, где схема заранее не известна. Основные сущности остаются нормализованными, потому что по ним нужны агрегаты и целостность.

### Особенности реализации
   - Версия сценария — это снимок того, что видел пользователь. Метаданные показа лежат в tour_versions, шаги — в hints, и обе таблицы замораживаются после публикации.
   - SDK получает опубликованный сценарий целиком за один запрос POST /v1/resolve с ключом приложения, поэтому гайд продолжает работать при временной потере сети.
   - Иммутабельность Published-версий. Опубликованные гайды нельзя редактировать. Гарантируется триггерами PostgreSQL.
   - Любое изменение создает новую версию (Draft). Это решает критическую проблему в аналитике, когда события от старых пользователей привязываются к новому тексту.
   - Реактивный SDK — SDK загружает декларативный сценарий и самостоятельно управляет показом шагов. Для обнаружения якорей используется polling (setInterval, ~200ms) + querySelector; позиционирование подсказок через getBoundingClientRect; прогресс хранится в sessionStorage, счетчики показов — в localStorage. SDK работает оффлайн после загрузки сценария и не требует императивных команд от сервера. События (tour_started, hint_shown и далее) отправляются батчами с повтором на 5xx и 429, event_key при повторе сохраняется, поэтому прием идемпотентен. Рекомендуемое улучшение: заменить polling на MutationObserver/IntersectionObserver.
   - Изолированный Builder через postMessage
   - Визуальный выбор элементов (якоря) открывается в отдельном окне. Это предотвращает конфликты CSS/JS с админкой и позволяет безопасно переиспользовать Builder на любых доменах сервисов через защищенный обмен JSON-сообщениями.
   - Строгий Workflow версионирования (Draft - Published - Archived + DB‑триггеры предотвращают слом аналитики и неправильные правки в проде)
   - Уникальные индексы в БД гарантируют, что у одного тура может быть только один активный Draft и одна Published версия. Откат к старой версии осуществляется копированием архивной версии в новый Draft.

## Линтеры
Оба линтера запускаются в CI (.github/workflows/ci.yml) вместе со сборкой и тестами.

Backend — golangci-lint v2.12, конфигурация в .golangci.yaml в корне проекта. Взят стандартный набор (errcheck, govet, ineffassign, staticcheck, unused) без добавления экзотики: он ловит реальные ошибки и почти не дает ложных срабатываний. Из errcheck исключены три вызова, где ошибка отбрасывается осознанно, и проверка была бы шумом:
- ctx.Error у Gin вызывается ради побочного эффекта, ошибку возвращает только при nil-аргументе
- отложенный tx.Rollback после успешного коммита всегда возвращает ErrTxClosed, это штатный путь
- отложенный db.Close на соединении, которое и так закрывается

Frontend — ESLint 10 (flat config, frontend/eslint.config.js): рекомендованные наборы js и typescript-eslint, правила react-hooks (включая правила React Compiler) и react-refresh. Три правила React Compiler (set-state-in-effect, immutability, purity) временно понижены до warning: они указывают на настоящие анти-паттерны в нескольких компонентах, но их починка требует переработки состояния этих экранов и вынесена из задачи подключения линтера.

## Ограничения MVP
Сознательные упрощения и незакрытые места, чтобы их не пришлось выяснять по коду:
- Страницы аналитики в админке нет, метрики доступны через GET /v1/tours/{tourId}/analytics.
- Формирование PDF-отчета не реализовано: в схеме есть таблица reports под статус и путь к файлу, кода генерации пока нет.
- Часть админки (список сценариев, удаление, загрузка тура для редактирования) работает поверх localStorage, через API идут создание тура, создание подсказок и публикация.
- Редактирование уже созданного тура из интерфейса не поддерживается, форма сохранения возвращает ошибку.
- SDK не собирается отдельным бандлом: это React-компоненты внутри того же приложения, а не подключаемый script tag. Модель подключения (публичный ключ приложения, список разрешенных origin) в API уже заложена.
- allowed_origins не проверяется: CORS-мидлварь отражает любой присланный Origin. Поле хранится и отдается в API, но ограничения не дает — на проде это надо чинить.
- Вход по http держится на полифилле crypto.subtle, а не на настоящем secure context. Транспорт при этом остается незашифрованным: токены идут открытым текстом.
- Админские ручки закрыты OIDC: нужен заголовок `Authorization: Bearer <id_token>` и членство в одной из групп `oidc.admin_groups`. Роли живут в провайдере, таблицы пользователей у сервиса нет. Сервис не стартует, пока issuer не отвечает на discovery-запрос.
- `tour_versions.created_by` пока не заполняется: колонка есть и читается, но кто создал версию — не записывается.
- Демо-классифайд аутентифицирует только GET /v1/users/me и тем же провайдером, что и админка, но без проверки групп. Лента объявлений остается публичной. Сервис не стартует, пока issuer не отвечает на discovery-запрос, поэтому секция oidc обязательна и для него. Ключ admin_groups в общем конфиге демо-сервис не читает.
